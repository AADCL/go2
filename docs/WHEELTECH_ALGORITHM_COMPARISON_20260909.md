# GO2 V2.0.0 与 WheelTech V5.1 算法对比

本文保留 2026-09-09 的历史对比。V2.1.0 已适配 WheelTech 的离线分布式 PMF/鲁棒平面重建，当前实现与许可证边界见 [V2.1.0 发布说明](RELEASE_NOTES_V2.1.0.md) 和 [通用导出修复](TERRAIN_EXPORT_REVISION2_20260910.md)。

## 1. 对比基线

- GO2：机器狗 1 `/home/nvidia/go2_nav_ws` 于 2026-09-09 验证通过的端侧状态。
- WheelTech：`AADCL/ugv` 的 `main`，提交
  `47d04a57b410b95715114215c63c05f1ede5bd5e`，目录 `WheelTech/`。
- 本文只比较算法、数据契约和安全架构。车体尺寸、传感器安装、底盘接口和速度上限等硬件差异不作为优劣结论。

## 2. 共同架构

两套系统目前共享以下核心路线：

1. FAST-LIO 提供连续激光惯性里程计和配准点云。
2. 保存地图时使用两级体素结构，以粗粒度贝叶斯状态判断动态/静态，以细体素保存交付几何。
3. 自由空间使用三维 DDA 射线，动态物体离开后通过连续 miss 证据清除。
4. 地形在建图结束后离线重建，PMF 只提供保守种子，连续局部平面恢复坡面。
5. PGM 是全局静态占据权威，保存的 2.5D 数据只向已知可通行区域叠加坡度代价。
6. 全局规划考虑坡度，局部 costmap 不加载保存的坡度/高程层。
7. 局部障碍由当前帧 Patchwork++ 地面分割得到，`observation_persistence=0`，避免旧动态点拖影。
8. 全局使用 GlobalPlanner，局部使用 TEB，均未启用障碍速度预测。

## 3. 主要差异

| 模块 | WheelTech V5.1 | GO2 V2.0.0 | 影响 |
| --- | --- | --- | --- |
| 射线位姿 | 使用 FAST-LIO 点云和里程计接口，轨迹另存 | `/odom_robot` 六自由度位姿按点云时间戳匹配，并结合 `base_link -> lidar_link` 计算真实雷达原点；`/odom_nav` 只记录轨迹 | GO2 对坡道、俯仰和队列延迟更严格 |
| 贝叶斯 miss | `p_miss=0.30` | `p_miss=0.40` | GO2 单次自由证据更弱，优先避免稀疏静态结构被过度清除 |
| 已确认体素删除 | 8 次 miss、0.75 s | 12 次 miss、1.20 s | GO2 更保守，动态残影消失更慢，但地图完整性更好 |
| 射线端点保护/候选超时 | 0.20 m / 3 s | 0.25 m / 6 s | GO2 更容忍 Mid-360 端点抖动和短时遮挡 |
| 细体素状态 | 父粗体素 generation 绑定 | 除 generation 外，显式增加细体素 6 次/0.5 s/50% 晋升和 50 万候选预算 | GO2 对细节复活和内存上限控制更明确 |
| 动态调试点 | 配置默认发布 | 生产默认关闭 | GO2 降低运行带宽和 CPU 负担 |
| 地形种子与坡度 | PMF 窗口 101，最大连续地面坡度 25° | 轨迹锚定候选 + PMF 重捕获，最大连续地面坡度 35° | GO2 面向四足可通行坡度，并解决短轨迹/室内 PMF 过严问题 |
| 地形质量门 | 连通地面和局部平面规则 | 额外检查轨迹追踪、平面拟合保留率、连通率、基底自由区 8%、轨迹走廊 95%、基底 known 保持 | GO2 更强调导出事务是否完整，而不只看是否生成文件 |
| 地图提交 | `finalize_map.py` 串联多个工具 | 唯一 export ID、源 PCD 快照校验、隐藏 staging、metadata-last、15 项 SHA256 校验 | GO2 对中断、旧输出误判和半提交更严格 |
| 全局坡度层 | 对已知 PGM 单元取更高代价 | 同原则，并要求网格尺寸/原点/分辨率精确一致；禁止加载到 rolling costmap，支持安全 reset 重放 | GO2 插件的生命周期和几何契约更严格 |
| 全局/局部膨胀 | 0.15 m / 0.22 m | 0.10 m / 0.10 m | GO2 是用户确认的 0.64 m 窄通道配置，净空更小，必须使用真实 footprint 验证 |
| 实时地面分类 | 栅格局部平面、坡度 22°、台阶 0.08 m；主要输出诊断和障碍云 | 连接地面、低支撑带、连续陡坡识别、天花板排除、雷达高度 Huber 拟合和健康滞回 | GO2 能避免 8–35° 连续坡面被局部硬障碍化，并能区分软几何波动与硬故障 |
| 地形健康联锁 | 没有把 terrain diagnostics 接入目标和底盘速度总门控 | `/terrain/healthy` 同时约束 navigation supervisor 和 velocity shaper | GO2 在雷达/地面链异常时会取消目标和截断速度 |
| Goal 生命周期 | RViz/action 直接进入 `move_base` | Supervisor 隔离公开/内部 action，要求定位、控制、地形和内部 server 同时就绪；失效后拒绝旧 Goal | GO2 解决了“有路径但第二次不执行”和恢复后旧目标突然继续的问题 |
| Recovery | `StartEscapeRecovery`，只有后向点云新鲜且覆盖足够才允许短距倒退 | 只清理局部动态障碍层；TEB 可给出受限倒车，SDK bridge 另有速度和响应保护 | WheelTech 多一个显式起步脱困算法；GO2 当前避免自动恢复动作造成拖脚或盲区倒退 |
| 定位健康 | FAST-LIO + NDT 重定位，定位和导航分开启动 | NDT 分数/跳变/超时 guard、唯一 `map -> odom`、Goal/控制联合门控 | GO2 的定位故障传播到运动停止更完整 |
| 启动与兼容 | 定位、导航和地图收尾分别执行 | `run_go2` 统一锁、进程冲突检查、旧地图 legacy 模式和新地形地图严格模式 | GO2 更适合现场重复操作和多地图回滚 |

## 4. GO2 当前仍未采用的 WheelTech 机制

### 4.1 StartEscapeRecovery

GO2 没有移植 WheelTech 的起步倒退恢复插件。该插件的安全价值在于同时检查全局/局部代价和后向点云覆盖；但 WheelTech 文档已记录 Mid-360 后方近场无点时会拒绝执行。GO2 若后续增加该能力，必须先在机器狗安装姿态下验证后向 `0.15-0.70 m` 的连续覆盖，不能直接关闭后向观测门。

### 4.2 更强的动态清除

WheelTech 的 `p_miss=0.30`、8 次/0.75 s 删除比 GO2 更积极。GO2 曾出现地图被滤除过重，因此当前使用 `p_miss=0.40`、12 次/1.20 s。后续只能通过带人员横穿和细杆/墙边保留真值的 bag A/B 回放决定是否折中，不能单独为了更快消除残影降低门限。

### 4.3 更大的局部安全膨胀

WheelTech 局部膨胀为 0.22 m，GO2 按 0.64 m 通道需求设为 0.10 m。GO2 的配置可通过性更高，但对点云噪声、站姿摆动和通道测量误差更敏感。当前不得继续缩小 footprint 或 TEB 障碍距离。

## 5. GO2 特有的工程增强

- 地图构建、保存和导出均有容量限制、原子快照和跨文件一致性检查。
- 新地图地形资产缺失或校验失败时拒绝导航，不静默退回 legacy；旧地图则显式兼容。
- Terrain Guard 的硬故障包括输入断流、低频、Frame/时间戳错误、处理超时、平面残差过大和传感器高度越界。
- Terrain Guard 的面积、近场支撑和扇区不足属于有界软失败。机器狗 1 实测通常只能覆盖 2–3 个扇区，因此生产配置使用最少 2 个扇区，其他平面和高度门保持不变。
- SDK bridge 提供电池、BMS、关节、IMU、步态响应和最后一次 SDK 返回码，速度整形器额外监控地形健康和命令新鲜度。

## 6. 后续建议

1. 用同一组静态细障碍、人员横穿和坡道 bag，对 `p_miss=0.30/0.35/0.40` 与删除持续时间做离线 ROC 对比。
2. 记录不同房间、墙角和坡道的 `covered_ground_sectors` 分布，确认 2 扇区门限不会掩盖真实地面退化；硬故障门不得放宽。
3. 只有补充后向传感器或证明 Mid-360 后方近场覆盖后，再评估 StartEscapeRecovery。
4. 将 footprint、膨胀和 Terrain Guard 扇区门限做成每台机器人独立 profile，算法源保持一致。
5. 保持局部无保存坡度层；如未来需要本地陡坡保护，应新增实时重力坡度判定，而不是查询会随 `map -> odom` 修正漂移的旧高程。
